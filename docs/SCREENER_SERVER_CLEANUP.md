# Скринер: что можно удалить на сервере

Дата решения: 2026-07-26. Клиент переехал с серверного графика спреда на
собственный, который строится напрямую из публичного REST бирж (тот же движок,
что на вкладке «Калькулятор/Арбитраж»). От сервера скринеру теперь нужны **только
сигналы, каталог инструментов и конфиг**.

Клиентская часть переезда уже сделана и в приложении не осталось ни одного
вызова перечисленного ниже. Порядок отключения на сервере — на ваше усмотрение,
клиент к этому готов.

---

## 1. Что удалять

### 1.1 WebSocket: поток графика (`watch`)

Спека — [SPREAD_CHART_SERVER_SPEC.md](SPREAD_CHART_SERVER_SPEC.md), описание
протокола — [CLIENT_INTEGRATION.md §2.45](CLIENT_INTEGRATION.md).

Удаляется целиком:

| Направление | Сообщение |
|---|---|
| client → server | `watch` |
| client → server | `unwatch` |
| server → client | `watch_snapshot` |
| server → client | `spread_tick` |

Вместе с ними уходит вся обвязка:

- лимит **3 одновременных watch на сессию** и ошибка при его превышении;
- ошибка «инструмент торгуется меньше чем на 2 площадках» в контексте watch;
- сброс watch'ей при закрытии сокета и правило «`subscribe`/reconfigure не
  отменяет watch'и»;
- параметры `window_ms`, `resolution_ms`, `long_exchange`, `short_exchange`
  в сообщении `watch`.

### 1.2 REST: история спреда

| Эндпоинт | Примечание |
|---|---|
| `GET /spread/history` | клиент не вызывал его и до переезда |
| `GET /spread/range` | «История за 3 дня» из UI убрана |

### 1.3 Хранение истории спредов (главная экономия)

После удаления §1.1 и §1.2 серверу больше не нужно **ничего накапливать по
спредам**:

- **тонкий слой** — посекундная лента по парам площадок за последние минуты
  (та, что кормила `watch` и `/spread/history`);
- **грубый слой** — поминутные бакеты min/max/close за дни, под `/spread/range`.
  По оценке из [CLIENT_INTEGRATION.md §2.46](CLIENT_INTEGRATION.md) это ~300 КБ
  на монету за 3 дня и **~100+ МБ** на несколько сотен монет.

Сигналам история не нужна: динамика (`baseline_pct`, `z_score`, `episode_ms`)
считается на своём коротком окне внутри движка сигналов и остаётся как есть.

### 1.4 Ключи конфига

| Ключ | Где | Что с ним |
|---|---|---|
| `history_window_ms` | ClientConfig | удалить — это лимит окна `/spread/range` |
| `chart.history_window_ms` | серверный конфиг | удалить вместе с грубым слоем |
| `chart.history_resolution_ms` | серверный конфиг | удалить вместе с грубым слоем |
| `max_chart_spread_pct` | ClientConfig | **проверьте перед удалением** (см. ниже) |
| `chart.sanity_max_spread_pct` | серверный конфиг | оставить, если он же режет аномалии в сигналах |

> ⚠️ `max_chart_spread_pct` описан как отсев аномалий **только для backfill и
> тиков графика**. Если по коду он влияет исключительно на watch-поток — в
> утиль. Если через него же (или через `chart.sanity_max_spread_pct`) режутся
> аномальные котировки на входе в движок сигналов — **оставить**, иначе в
> сигналы полезут битые цены. Это единственный пункт списка, который нельзя
> удалять не глядя в код.

Клиент оба ключа больше не отправляет и не показывает в фильтрах.

## 2. Что оставить — это по-прежнему используется

**WebSocket `/ws`:**

- `subscribe` / `subscribed` (handshake + эхо эффективного конфига);
- `config` push сразу после connect;
- `universe` — каталог инструментов, кормит вкладку «Вселенная»;
- `event` — сигналы, основной поток;
- `error`;
- `ping` / `pong`.

**REST:**

| Эндпоинт | Кем используется |
|---|---|
| `GET /summary` | «вход сейчас» на карточках сигналов и колонка спреда во «Вселенной»; клиент опрашивает раз в 10 с, пока экран открыт |
| `GET /config` | экран фильтров |
| `POST /config/validate` | валидация фильтров до применения |
| `GET /healthz` | ливнесс |

`GET /instruments` и `GET /why` клиент не вызывает (каталог приходит по WS), но
это не следствие переезда — трогать их или нет, решайте отдельно.

---

## 3. Что НЕ меняется, хотя могло показаться

**Список бирж остаётся полным** (`bybit`, `okx`, `mexc`, `bitget`, `gate`,
`coinex`, `kucoin`, `phemex`). Приложение умеет строить график только по пяти
площадкам, для которых у него есть market-data провайдер, но конфиг скринера
общий на весь сервер — менять его ради одного клиента неправильно. Поэтому
сигналы и строки каталога по `coinex` / `kucoin` / `phemex` **фильтруются на
стороне клиента**. Сервер продолжает их считать и присылать.

Если для этих площадок появятся провайдеры в приложении, фильтр снимается — со
стороны сервера ничего делать не потребуется.

---

## 4. Как проверить, что клиент отвязался

- за сессию работы приложения в логах сервера нет ни одного `watch` / `unwatch`;
- нет запросов на `/spread/history` и `/spread/range`;
- открытие экрана монеты не порождает вообще никакого трафика к скринеру — он
  идёт напрямую на биржевые публичные REST.
